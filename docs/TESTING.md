# 테스트와 측정 결과

> 측정일 2026-10-09. 측정 환경: Windows 11 Pro, 18 논리 코어, 16GB RAM, Node 24.16, wrangler 4.148.0(workerd 1.20261006.1).
> **아래 부하 수치는 모두 로컬 `wrangler dev`(workerd 프로세스 1개, 같은 PC 에서 부하 생성) 결과이며 Cloudflare 실제 배포의 성능이 아닙니다.**
> 클라우드 시험도 강당 LTE·5G 혼잡을 재현하지 않습니다.

## 3. 부하 시험 도구

실제 참가자 경로만 사용합니다: `POST /api/join`(코드 입장, 쿠키 발급) → `GET /ws?role=p`(쿠키·Origin 확인) → `POST /api/answer`.
진행은 진행자 API(로그인·명령·내보내기)로 합니다. 우회 경로나 시험용 백도어는 없습니다.

```bash
node loadtest/run.mjs --base http://127.0.0.1:8787 --n 500
```
```bash
node loadtest/run.mjs --base http://127.0.0.1:8787 --n 1000 --hold 30 --max-conn 200
```

| 옵션 | 기본값 | 의미 |
|---|---|---|
| `--n` | 500 | 참가자 수(새 시험 행사를 만들고 `부하####` 코드 생성) |
| `--hold` | 20 | 연결 유지 관찰 시간(초) |
| `--spread` | 1000 | 집중 제출 시작 분산 구간(ms) — "약 1초 안에 제출 시작" |
| `--drop` | 0.3 | 2번 문제에서 강제로 끊었다가 지수 백오프로 재접속시킬 비율 |
| `--abort-sim` | true | 2번 문제에서 일부 요청을 응답 전에 끊고(5ms) 같은 reqId 로 재시도 |
| `--max-conn` | 0(무제한) | 생성기 HTTP 연결 수 상한(Windows 로컬 시험용) |
| `--max-requests` / `--max-seconds` | 20000 / 900 | 안전 상한. 넘으면 중단하고 결과 저장 |
| `--cloud-ok` | — | 로컬이 아닌 주소에는 이 옵션이 있어야 실행 |
| `--event` | — | 기존 행사 재사용(그 행사의 부하시험 코드 사용, 시작 시 초기화) |

시나리오: ① 입장+WebSocket → ② 연결 유지 → ③ 1번: 전원 집중 제출 → 2번: 혼합(답 수정·동시 중복·순서 뒤바뀜·응답 유실 재시도·연결 30% 끊김과 재접속) → 3번: 집중 제출 → ④ 결과 비교.
봇은 실제 휴대폰 화면과 같은 규칙으로 재시도합니다(네트워크 오류·5xx·429 → 같은 reqId·seq, 백오프, 마감되면 중단).
비교: 접수 응답을 받은 답이 서버에 없거나 옛 버전이면 `lostAccepted`(0이어야 함), 서버 저장 답을 독립적으로 다시 채점한 수와 서버 집계 일치(`gradingMatches`), 접수 응답 기준 예상 집계 일치.
결과는 `loadtest/results/*.json`(git 제외)에 저장. 생성기 CPU·이벤트 루프 지연도 기록합니다.
`Server-Timing: do;dur=` 헤더로 **서버(Worker)가 잰 DO 왕복 시간**을 따로 기록해, 네트워크·생성기 지연과 구분합니다.

2번(혼합) 문항의 접수 확인 시간에는 **의도적인 수정 간격·재시도 대기**가 포함되어 있어 1·3번과 직접 비교하지 않습니다.

### 해석
- **정확성**: 모든 유효 시험에서 접수 응답을 받은 답의 손실·중복 0, 서버 집계 = 독립 재채점 = 예상 집계.
  로컬이 붕괴한 시험에서도 `lostAccepted = 0` 이었습니다(응답을 못 받은 요청만 있었음).
- **DO 처리 시간**: 1,000명 집중 제출 때도 DO 왕복 p95 119~254ms. 같은 시점 클라이언트 지연(1.6~2.2초)의 대부분은 DO 밖에서 쓰였습니다.
  로컬 관측 span 에서도 SQLite 실행은 평균 0ms(최대 5ms)였습니다.
- **로컬 오류의 원인**: 연결 무제한일 때 생긴 HTTP 500 은 wrangler 의 로컬 전용 중계 계층(ProxyWorker)의
  "Network connection lost / dropped connection to the UserWorker" 였고, 직전 TIME_WAIT 소켓이 8,000개를 넘었습니다.
  생성기 연결을 200개로 재사용하자 같은 시나리오에서 ProxyWorker 경고·500·연결 거부가 0건이 되었습니다.
  → 한 대의 Windows PC 에서 새 TCP 연결 수천 개를 여는 **시험 환경의 한계**로 판단합니다. 실제 휴대폰은 각자 Cloudflare 엣지에 연결하므로 이 결과로 클라우드 성능을 판단할 수 없습니다.
- **측정 중 발견한 시험 환경 문제**: 처음 몇 번은 이전 `wrangler dev` 가 완전히 종료되지 않아 **같은 포트를 3개 프로세스가 LISTEN** 하고 있었습니다(요청이 서로 다른 로컬 DO 로 흩어짐). 그 결과는 모두 버렸습니다.
- 목표(500명 p95 ≤ 2초)에 대해: 로컬에서는 817ms 였지만 **클라우드에서 검증하지 않았으므로 달성했다고 보지 않습니다.**

## 7. 클라우드 부하 시험 절차 (승인 후)

1. 시험용 Worker(`nobrain-festival-quiz-test`)에 배포되어 있는지 확인. 운영 행사가 진행 중이 아닐 것.
2. 진행자 비밀번호를 환경변수로:
   ```bash
   export HOST_PASSWORD='…'
   ```
3. 500명 1회:
   ```bash
   node loadtest/run.mjs --base https://nobrain-festival-quiz-test.sirlma.workers.dev --n 500 --cloud-ok --max-requests 6000 --max-seconds 600
   ```
4. 결과를 본 뒤 1,000명 1회(`--n 1000 --max-requests 12000`). 매번 새 시험 행사를 만듭니다(기존 행사에 영향 없음).
5. 중단: Ctrl+C (연결을 닫고 그때까지 결과 저장). 상한에 닿으면 자동 중단.
6. 생성기 PC 의 CPU·이벤트 루프 지연(결과 파일 `generator`)이 높으면 PC 를 나눠 실행하세요. 같은 공인 IP 에서 1,000명이 들어오는 것은 실제(통신사 다수 IP)와 다릅니다.
7. 사용량 확인: [COSTS.md](COSTS.md).
